# Barge

The user's request: $ARGUMENTS

1. Confirm the current directory is a Git repository with a GitHub `origin` and resolve the origin to `<owner>/<repo>`.
2. Select the flow from the user's request and the local repository's state — naming a Linear issue defaults to starting that issue fresh in the cloud, so "start fresh in the cloud" phrasing is not required; only an explicit request to hand off local work overrides that default. Check whether there is local work to preserve: `git status --porcelain` is non-empty, or the branch has an upstream and is ahead of it (`git rev-list --count @{u}..HEAD` is non-zero). A branch with no upstream configured is not by itself local work to preserve.
   - Treat a trailing `(alive)` marker in the user's request as an instruction to add `--alive` to the selected CLI command. Remove the marker from task text and Linear issue identifiers; do not send the literal marker as part of either value.
   - **Linear cloud start:** This is the default whenever the request names a Linear issue, unless the user explicitly asks to hand off local work instead — `/barge:handoff BSH-123` alone selects it, with no "start fresh" phrasing required. Resolve `<owner/repo>` from an explicitly requested target repository (including one named in the Linear issue itself, e.g. a "Target repository" field), otherwise use the local `origin`. Resolve the Git ref from an explicitly requested ref, otherwise use the remote default branch. Run `barge linear <owner/repo> <ref> <issue-id-or-url>` from the repository root. Add `--base <branch>` only when the user explicitly chose a non-default PR base. Do not create a continuation brief, package the local repository, or fall back to `barge create` when this command fails. The control plane folds the issue's comments, attachments, and linked or mentioned issues into the session task — including a referenced design issue's own text — so the worker resolves those references itself; a design source it cannot open stops the session as blocked rather than shipping unverified work.
   - **Cloud start without an issue:** Use this when the request explicitly asks to start fresh in the cloud but names no Linear issue (e.g. "start fresh in the cloud", "start this over in the cloud") — do not read "names no Linear issue" in the current-work bullet as covering this case, since `barge create` packages local state the user asked to leave behind. Resolve `<owner/repo>` and the Git ref the same way as above, and use the request's own text as the task. Run `barge cloud <owner/repo> <ref> "<task>"` from the repository root. Add `--base <branch>` only when the user explicitly chose a non-default PR base. Do not create a continuation brief, package the local repository, or fall back to `barge create` when this command fails.
   - **Current-work handoff:** Use this when the request names no Linear issue and is about continuing or handing off *current* work — a bare `/barge:handoff`/`$barge:handoff` with nothing else to go on, or phrasing like "hand this off", "continue in the cloud", "close my laptop and keep working" — or when the user explicitly asks to hand off local work despite naming an issue (e.g. "hand off my local work on BSH-267"). Issue-less requests that explicitly ask to start fresh in the cloud take the cloud-start bullet above instead. In the issue-named override case, fold the named Linear ID into the task title or brief for traceability. Summarize the active task into a temporary Markdown brief containing the goal, success criteria, decisions, completed work, important files, validation already run, unresolved issues, and next action. Do not include secrets or raw credentials. Run `barge create "<task>" --brief-file <brief-path>` from the repository root. Add `--base <branch>` only when the user explicitly chose a non-default PR base.
   - **Conflicting signals:** If the selected flow is a cloud start — the request names a Linear issue or explicitly asks to start fresh — but local work to preserve exists (per the check above) and the user has not explicitly chosen to discard it or hand it off, stop and ask the user whether to hand off the local work or discard it and start clean — do not silently choose either, since starting fresh discards local state irreversibly.
3. Return the session URL and state that the laptop is safe to disconnect only after the CLI reports that URL.
4. For a current-work handoff, if packaging blocks on a possible secret, report the kind and file from the CLI output and let the user remove it; never pass `--allow-secrets` automatically. Artifact packaging and `BARGE_ARTIFACT_KEY` do not apply to either cloud-start flow.

Requires the `barge` executable on `PATH` and stored credentials. The CLI reads `~/.config/barge/config` (written by `barge setup` / `/barge:handoff-setup`; the pre-rename `~/.config/cloud-handoff/config` also still works) itself — rely on `BARGE_URL`/`BARGE_TOKEN` only when they are already present in the environment; never set, export, or read the token into the conversation. If `barge` is missing or a call fails with missing credentials or 401, run `/barge:handoff-setup` instead of guessing at credentials.
